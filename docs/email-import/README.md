# PDFium Gate - Email Import

This directory is the design and working documentation for the Email Import subproject in PDFium Gate.

The goal is to let a user import an `.eml` or `.msg` message into Obsidian and turn it into a stable PDF document that can use the existing PDFium Gate workflow: reading, copying text, highlighting, categorization, metadata, document information, search, and links.

Email is treated as an **import source**, not as a new permanent working document type.

## Product model

The normal user-facing result of an email import is a PDF.

The PDF includes the message header/body and a human-facing attachment list. Technical provenance remains in the normal PDFium Gate metadata record rather than being exposed as documentary clutter in the visible PDF.

The original `.eml` / `.msg` file is not required to remain visible in the vault. The exact source bytes are retained unchanged in hidden SHA-addressed storage under `.pdf-metadata/emailsources/` and remain the forensic source of truth.

## Integrity and duplicate detection

Before conversion, PDFium Gate calculates SHA-256 over the original source bytes.

The SHA-256 value serves two purposes:

1. integrity evidence for the retained original source;
2. exact duplicate detection when the same source file is imported again.

The current automatic drag-and-drop flow opens an existing PDF for an exact duplicate instead of regenerating it. A future UX refinement may replace the automatic duplicate decision with an explicit user choice such as **Import again / Open existing / Cancel**; that change has not yet been implemented.

When available, the email `Message-ID` is retained as technical metadata. It may later support detection of the same logical message when two exported files are not byte-identical.

Attachments whose decoded payload bytes are available receive their own SHA-256. This allows extraction/import and clickable-PDF-link code to verify that the current vault target is byte-identical to the attachment embedded in the email.

## Implementation direction

The Email Import feature is designed as a main capability composed from small source modules rather than one large implementation file.

Implemented responsibilities include:

- EML parsing with `mailparser`;
- MSG parsing with `@kenjiuno/msgreader`;
- Canonical Email Document v1;
- shared SHA-256/integrity services and exact duplicate detection;
- safe HTML normalization/rendering;
- Chromium/Electron PDF generation;
- SHA-addressed source retention;
- automatic attachment extraction;
- PDF attachment registration and provenance;
- native Obsidian wikilink relationships for exported attachments;
- stable clickable attachment links inside generated email PDFs;
- projection into the existing `pdf/document` metadata record and Document Register model;
- build-time dependency bundling into the self-contained plugin runtime;
- explicit/manual Command Palette import as a fallback;
- automatic drag-and-drop import with settings-driven behavior and sequential multi-email processing.

Both EML and MSG normalize into the same Canonical Email Document v1. Outlook-specific CFBF/MAPI handling remains inside the MSG parser boundary, while downstream rendering, retention, attachment policy, metadata projection, PDF generation, and link handling remain source-format independent.

Permanent MSG verification uses deterministic synthetic CFBF/MSG sources generated by test code. Private real-world email is not required as a repository fixture.

Generated email PDFs remain ordinary PDFium Gate `pdf/document` records. Technical email provenance is stored as `email_import_*` properties in the same Markdown record without becoming default DocumentInfo/Bases columns. Compatible user fields such as date, time, and sender may receive initial suggestions without creating or redefining the user's schema.

## Automatic drag-and-drop milestone - practically verified

The preferred UX for Thunderbird-to-Obsidian import is automatic and settings-driven rather than modal.

Practically verified behavior includes:

- dropped `.eml`/`.msg` staging files import automatically when enabled;
- exact source bytes are retained in hidden SHA-addressed storage;
- generated email PDF is created in the drop folder;
- ordinary real attachments are automatically exported to the same folder when enabled;
- inline/CID resources stay internal to the message;
- verified PDF attachments become normal registered PDFium Gate documents;
- non-PDF attachments such as JPG, DOCX and XLSX remain normal vault files;
- exact duplicate drag/drop opens the existing PDF and does not create duplicate attachment copies;
- multiple dropped emails are serialized without modal dialogs.

Practical test points 1-11 for this flow were reported OK on 2026-09-29.

The old Command Palette import remains available as an explicit/manual fallback.

## Native attachment relationships - practically verified

The parent email PDF's existing `File Metadata` record contains a plugin-managed Markdown block with genuine Obsidian wikilinks to exported attachments:

```markdown
<!-- pdfium-gate:email-attachments:start -->
- [[Cases/Email/report.pdf]]
- [[Cases/Email/photo.jpg]]
- [[Cases/Email/letter.docx]]
<!-- pdfium-gate:email-attachments:end -->
```

The relationship is deliberately stored in Markdown rather than in a new database or in the user metadata schema.

Practical testing has confirmed:

- renaming an exported attachment inside Obsidian updates the native relationship;
- PDFium Gate can normalize Obsidian's shortened link text back to resolver-confirmed full vault-relative targets inside its own managed block;
- moving a target attachment to another Obsidian folder preserves the clickable link from the immutable email PDF.

The last point is important: current file location is resolved from the live Markdown relationship and verified attachment identity rather than from a static path embedded in the PDF.

See `ATTACHMENT-RELATIONSHIPS.md`, `ATTACHMENT-PDF-LINKS.md`, `DECISIONS-2026-09-29.md`, and `DECISIONS-2026-09-30.md`.

## Clickable attachment links inside generated PDFs - practically verified

Generated email PDFs render attachment filenames as real PDF link annotations using a stable identity URI:

```text
obsidian://pdfium-gate-email-attachment?source=<email-sha256>&attachment=<attachment-sha256>&index=<ordinal>
```

The PDF does **not** store the attachment's current vault path.

The user-verified click flow is:

1. existing PDF wrapper instrumentation records the physical click and its exact coordinates;
2. the Main Bridge resolves the exact embedded PDF target;
3. `src/platform/email-attachment-pdf-point.js` reuses the canonical Chromium RuntimeDriver for scroller geometry and PDF point conversion;
4. `src/email-import/attachments/pdf-link-hit-test.js` uses PDF.js annotations to determine whether the actual clicked rectangle contains PDFium Gate's owned attachment URI;
5. `src/plugin/email-import/email-attachment-link-controller.js` orchestrates the operation;
6. the existing Email Import attachment resolver reads the current Markdown wikilinks, lets Obsidian resolve their current paths, hashes candidate bytes, and opens the unique SHA-matching file.

An earlier `will-navigate` / `will-frame-navigate` forwarding prototype was rejected after practical testing showed that embedded Chromium PDF clicks did not reach that event path. The rejected forwarder and its regression test have been removed.

Practical testing on 2026-09-30 confirmed:

- clicking an attachment filename in the email PDF opens the intended attachment;
- moving the attachment to another folder does not break that PDF link;
- ordinary PDFium Gate click behavior continues to work.

Detailed architecture and safety properties are documented in `ATTACHMENT-PDF-LINKS.md`.

## Modular source structure

The Email Import implementation follows the same separation principles as the rest of PDFium Gate.

Important current boundaries include:

- `src/core/integrity/sha256.js` - generic exact-byte SHA-256 identity;
- `src/email-import/parsers/` - source-format parsing;
- `src/email-import/runtime/` - import/export orchestration and retained-source loading;
- `src/email-import/render/` - controlled HTML and PDF rendering;
- `src/email-import/metadata/` - Email Import metadata projection and managed attachment relationship block;
- `src/email-import/attachments/` - attachment policy, extraction, and pure PDF link hit-testing;
- `src/platform/email-attachment-pdf-point.js` - small injected platform adapter for click-coordinate translation;
- `src/runtime/chromium-pdf-runtime-driver.js` - the sole owner of Chromium `pdf-viewer` / Shadow DOM primitives;
- `src/plugin/email-import/` - Obsidian adapter, vault trigger, and attachment-link controller;
- `src/plugin/features/20-email-import.js` - durable Email Import integration/facade and SHA/metadata target resolution;
- `src/main-bridge/features/09-email-import.js` - narrow Main Bridge facade for email PDF generation and attachment-point resolution.

The adapters use explicit dependency injection rather than hidden peer-feature calls. Existing PDFium Gate plugin-port and architecture verification remains authoritative.

Modals remain passive decision surfaces. Parsing, hashing, retained-source verification, durable writes, metadata construction and rollback remain outside modal classes.

The detailed architectural rationale remains in `REFACTORING-AND-SHARED-SERVICES.md`.

## Regression tests under `scripts/`

Email Import keeps behavior checks in small focused scripts. Relevant attachment-link tests include:

- `test-email-import-renderer.js` - stable attachment URI generation and sanitization boundary;
- `test-email-import-pdf-electron.js` - real Chromium print-to-PDF preserves the custom URI;
- `test-email-import-attachment-links.js` - managed Markdown relationship behavior;
- `test-email-import-pdf-point-adapter.js` - wrapper click to PDF point boundary using the canonical RuntimeDriver;
- `test-email-import-pdf-link-hit-test.js` - owned annotation hit, ordinary-link pass-through, and ambiguity fail-closed behavior;
- `test-email-import-obsidian-adapter.js` - opening the current vault file.

Automated tests supplement practical Obsidian testing; they do not claim to reproduce the full embedded Chromium/Obsidian click chain.

## Next architectural/product milestones

The clickable attachment-link architecture itself is now practically verified. Remaining work should be treated as separate bounded milestones, including:

- duplicate-import UX: warn and let the user choose Import again / Open existing / Cancel;
- metadata/document-register maintenance when users delete documents or attachments;
- explicit diagnostics and repair tooling for missing or orphaned metadata relationships;
- further deletion/backlink behavior tests for non-PDF attachments.

The shared SHA/integrity layer also leaves room for a future vault-wide byte-identical duplicate finder, but that remains a separate project.

## Rendering and PDF generation

The normalized email is rendered using a controlled HTML shell and the Chromium/Electron environment available to Obsidian Desktop. Electron PDF generation crosses an explicit main-process adapter/transport boundary so parser and renderer code remain independent from Electron window APIs.

The legacy `html-pdf` conversion path from the reference Eml-Parser project is not part of the PDFium Gate architecture.

## Development method

Development takes place on the `feature/email-import` branch until the feature reaches an explicitly tested integration point.

The project follows these principles:

- document architecture as it evolves;
- keep existing PDF behavior unchanged;
- add one bounded capability at a time;
- keep Chromium viewer internals behind the RuntimeDriver boundary;
- use synthetic test messages rather than private mail as permanent fixtures;
- combine automated checks with explicit practical Obsidian testing;
- record design changes and rejected approaches;
- promote genuinely generic mechanisms to shared project services instead of coupling unrelated future features to Email Import.
