## Critical new finding: the prototype already writes full paths

Do **not** start the next conversation by merely changing the link generator from basename to full path.

`src/email-import/metadata/email-attachment-links.js` already receives the exported attachment's full vault-relative path and creates:

```js
return `[[${path}]]`;
```

The user later observed links such as:

```markdown
- [[Ekte Rått Ungt 1.docx]]
- [[Howard Moskowitz3.jpg]]
```

This happened after Obsidian had maintained/updated the native link.

Therefore the important conclusion is:

> PDFium Gate initially writes the full vault-relative path, but Obsidian may rewrite the textual wikilink to its shortest unambiguous representation during automatic link maintenance.

The user prefers an architecture where the relationship visibly identifies the intended document and does not leave doubt about which same-named file is meant.

## Next focused problem

Find the best way to preserve **native Obsidian relationship behavior** while making the target **visibly unambiguous**.

Constraints:

1. Keep genuine Obsidian links and Obsidian's resolver/link index.
2. Do not introduce a parallel attachment-path database merely to mirror rename/move state.
3. Prefer a visible full vault-relative path or an equivalently unambiguous representation.
4. Do not silently change the user's global Obsidian link-format setting.
5. Duplicate basenames in different folders must fail or resolve safely, never silently point to the wrong attachment.
6. If PDFium Gate must normalize its own generated block after a rename/move, scope that rewrite only to the plugin-managed block.
7. Preserve the retained EML/MSG as the immutable source of attachment bytes and provenance.

Before implementing a custom rename rewrite, inspect current Obsidian APIs/settings behavior and test whether an official link representation/API can preserve an explicit full target while still receiving native automatic updates.

## Known technical review points

These are not the next product decision, but should remain visible:

1. `beforeCreateAttachment` currently calls `suppressPathOnce` for every attachment target. The vault trigger only consumes suppression for EML/MSG paths, so non-email attachment paths may remain unnecessarily in the suppression set. Before freezing the feature, restrict suppression to `.eml/.msg` targets or make `suppressPathOnce` ignore other extensions.
2. Obsidian `create` timing after an external drag/drop may theoretically expose a source before copy completion. Current practical single/multi-email tests succeeded. Add bounded source-stabilization retry only if real failures appear; do not add complexity preemptively.
3. Partial attachment failure currently keeps successful attachments and the safely retained parent source. This is intentional fail-safe behavior but should be frozen/documented before release.
